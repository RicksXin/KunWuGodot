# 《昆吾禁地》Godot 数值设计与配表边界

版本：Godot-0.3  
日期：2026-08-11  
状态：当前工程数值事实索引；D0 兼容值与 1.0 正式值明确隔离

本文说明 Godot 工程中数值文件的位置、消费边界和校验方式，不重新定义产品数值。历史曲线推演、
旧存档迁移记录和迁移前工具链保存在
[`LegacyCocos/13_数值设计方案.md`](LegacyCocos/13_数值设计方案.md)，只用于审计。

## 1. 事实源顺序

数值冲突按以下顺序处理：

1. `Docs/1.0策划案/数值/`：规则和长期曲线的策划源头。
2. `Docs/PRD/`：面向 1.0 实现与验收的冻结值。
3. `res://data/`：已迁入 Godot 的机器可读表。
4. `res://scripts/`：当前 D0 可玩闭环的实际消费方。

存在数据文件不等于运行时已经接入。表、PRD 与实现不一致时必须登记差异，不允许任选一套数值。

## 2. 当前数值文件

| 文件 | 内容 | 当前状态 |
|---|---|---|
| `res://data/balance/combat_constants.json` | 生命系数、行动间隔、最小伤害、减伤等级常数 | 兼容配表；D0 战斗主要读取 `combat_d0.json` |
| `res://data/balance/growth_rates.json` | 旧六职业七维成长率 | 兼容和迁移输入；1.0 四职业/八分支待独立实现 |
| `res://data/balance/spiritual_root_multipliers.json` | 六档灵根初始与成长倍率 | 已进入数据校验；1.0 消费方待实现 |
| `res://data/balance/realm_ranges.json` | `Lv1–60` 兼容境界区间 | 1.0 正式范围只使用 `Lv1–30` |
| `res://data/balance/production_rates.json` | 迁移前候选方案 B | 不由当前 D0 运行时消费，也不是 PRD-03 正式值 |
| `res://data/config/combat_d0.json` | D0 固定遭遇技能、单位和战斗常数 | 已由 `KWCombatResolver` 消费 |
| `res://data/config/ling_pu_config.json` | D0 杂役招募与前三资源储量 | 已由 `Game` autoload 消费 |

七维内部键冻结为：

```text
strength magic technique speed constitution armor resistance
```

任何表、存档或 GDScript 领域对象都不得改用显示名作为内部键。

## 3. 兼容成长与灵根表

`growth_rates.json` 使用千分位整数表示每级成长：`3000` 表示每级 `+3.0`。每个职业必须完整
提供七维键，且不能出现未知键。表中的体修、武修、潜修、法修、医修、符修是迁移兼容数据，
不自动扩大 1.0 的职业范围。

六档灵根倍率如下：

| 灵根 ID | 初始倍率 | 成长倍率 |
|---|---:|---:|
| `mixed_root` | 100% | 100% |
| `pseudo_root` | 108% | 110% |
| `triple_root` | 116% | 122% |
| `dual_root` | 124% | 136% |
| `heavenly_root` | 133% | 152% |
| `variant_root` | 152% | 190% |

Godot 校验器要求两条倍率严格递增，最高成长倍率不得超过 200%。正式成长消费方实现前，
这些表只作为可校验输入，不应被 UI 直接读取并临时拼公式。

## 4. 战斗数值边界

D0 固定遭遇的事实源是 `res://data/config/combat_d0.json`，数据流固定为：

```text
CombatCommand → KWCombatResolver → CombatEvent → scripts/scenes/combat.gd
```

表现层只能播放结果，不得重算伤害或治疗。`combat_constants.json` 中保留的等级减伤曲线为：

```text
K(L) = 100 + floor(24 × (L - 1) / 10)
```

该曲线是 1.0 领域实现的候选兼容输入；在等级战斗系统正式落地并增加 GDScript 领域测试前，
不得替换 D0 固定遭遇的常数。

## 5. 灵源院三套数值不可混用

当前工程同时保存 D0 可玩值、迁移前候选表和 1.0 PRD 冻结值。三者用途不同：

| 口径 | 周期 | 单人产出（粮/木/铁/晶/庚） | 单人灵粮维护 | 消费状态 |
|---|---:|---|---|---|
| D0 当前运行时 | 30 秒 | `1/1/1/1/1` | `0/2/3/4/9` | `Game.settle_production()`；当前 UI 只开放粮/木/铁 |
| 兼容候选表 B | 30 秒 | `2/1/1/1/1` | `0/1/2/3/6` | 仅 `production_rates.json` 与历史审计使用 |
| 1.0 PRD-03 | `30/25/20` 秒 | `12/6/3/1/每2周期1` | `0/2/2/2/2` | 尚未接入 Godot 运行时 |

1.0 储量、杂役上限和招募成本也与 D0 的 `ling_pu_config.json` 不同。正式升级必须作为独立功能
变更完成数据迁移、UI 状态、离线结算和存档验收，不能在“引擎迁移”中静默替换。

## 6. Godot 加载与校验

Godot 不使用资源 Bundle。JSON 通过 `FileAccess.open("res://data/...")` 读取；当前 D0 的配置加载
集中在 `Game._load_json_tables()`。balance 表在正式消费方完成前由以下校验器负责结构验证：

```bash
/Applications/Godot.app/Contents/MacOS/Godot \
  --headless --path . --script res://tools/validate_project_data.gd
```

校验范围包括：

- 必需 JSON 可解析且根节点为对象；
- 七维成长键完整、无未知键且值为非负整数；
- 六档灵根完整并严格递增；
- 战斗常数为合法正数；
- 兼容生产表的岗位、周期和停工顺序结构完整；
- 境界区间连续且覆盖 `maxLevel`；
- 地图 manifest 的 `res://` 路径存在。

结构校验不证明数值已经符合 PRD，也不替代战斗、经济仿真或人工体验验收。

## 7. 后续落地顺序

1. 先按 PRD 冻结待实现版本的数值与存档迁移口径。
2. 在 `scripts/domain/` 增加独立 GDScript 领域对象和测试，不把公式写进 UI。
3. 让 `Game` 或结算器显式注入版本化表，保留旧档迁移时刻的冻结快照。
4. 运行数据校验、场景加载和对应领域测试。
5. 最后在 Godot 编辑器完成人工节奏、反馈和存档恢复验收。

当前优先差异是 PRD-03 灵源院正式数值尚未接入；这是已知产品实现缺口，不是文档迁移遗漏。
