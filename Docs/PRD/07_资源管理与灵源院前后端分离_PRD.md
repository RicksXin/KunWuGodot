需修正的实现差异：

- D0 配置把灵石列为生产岗位；1.0 应生产灵晶，二者不可直接改名合并余额。
- 当前配置为固定费用一次招募 5 人；1.0 为逐人招募、递增费用、最多 12 人。
- 当前有 `maxOfflineCycles` 截断；1.0 不设独立离线上限。现代码还保留剩余时间锚点，不能将该字段误描述为已正确丢弃超限收益。
- 当前整段汇总产粮、再按停工优先级处理维护；1.0 要按周期支付完整岗位维护，按灵木→玄铁→灵晶→庚精顺序分配粮食，不能借未来产粮提前供养。
- 当前灵粮结果使用 `maxi(旧库存, 新库存)`，可能掩盖维护导致的净减少；验收必须覆盖粮食实际下降。
- 当前岗位没有庚精逐名杂役的双周期余数；储量表不完整，缺少灵液动态周期和相应领取事务。

## 3. 已确认产品决策

确认依据：用户于 2026-09-15 指定“Q4：不继续耗粮了；Q9：可以在后台修改余额；其他按推荐来”。以下替代 0.1 的候选方案。

| ID | 决策 | 已确认方案 |
|---|---|---|
| Q1 | 玩家结算 | 服务端决定库存和收益；Godot 提交操作、显示结果 |
| Q2 | 断网 | 可查看最后状态，暂停分配、招募和消费等资源变更；重连补算生产收益 |
| Q3 | 身份与旧档 | 开发期独立测试身份、新建服务端测试档，保留当前存档；正式身份与迁移上线前另审 |
| Q4 | 满仓 | 对应岗位自动停工，不继续耗粮，不累计隐藏产量；有空间后自动恢复 |
| Q5 | 周期顺序 | 周期开始先用已有灵粮支付维护，周期结束入库产物；本周期新粮不能提前供养 |
| Q6 | 进度 | 内部稳定杂役标识；调岗携带个人周期进度；庚精 0/1 成功周期余数离岗冻结，新杂役从零开始；加速保留未完成周期比例 |
| Q7 | 配置生效 | 按生效时间分段结算；降容量不销毁已有库存，超容量按满仓停工 |
| Q8 | 接入范围 | 先独立测试闭环；正式在线接入前将所有影响五类资源余额的入口接入统一账本 |
| Q9 | 后台改余额 | 允许有权限的管理员修改玩家余额，操作必须经统一资源事务，记录操作人、原因与前后余额 |

测试身份不得用于公开生产环境。正式账号与旧档迁移仍为后续上线事项，不阻塞本期独立测试闭环。

## 4. 资源分类与管理边界

| 类别 | 内容 | 管理规则 |
|---|---|---|
| 生产资源 | 灵粮、灵木、玄铁、灵晶、庚精 | 公共资源栏，分别受储量等级限制，生产自动入库 |
| 货币/成长资源 | 灵石、魂晶 | 公共钱包，不读取灵源院容量，不在灵源院生产 |
| 材料、加工品、食物、资源包 | 沿用材料分册 | 百宝库堆叠库存，使用来源对应的容量与消费规则 |
| 装备 | 装备实例 | 沿用装备仓位，不用资源余额替代实例 |
| 任务物、蓝图、灵息、杂役 | 保护物或专属状态 | 不作为普通生产资源；灵液是永久状态，不进背包 |

`V10-RES-001`：统一稳定资源 code、名称键、分类、图标、存放位置、容量策略、来源及用途引用。客户端、后台、奖励和配方共享 code；禁止按中文名称或数组顺序匹配。

`V10-RES-002`：发布前建立旧字段与正式 code 的映射表，重点区分灵晶、灵石、魂晶。没有明确迁移依据的余额不得转换；天符玉兼容字段不因此重新开放。

`V10-RES-003`：容量策略按来源区分。生产溢出丢弃；资源包等是否要求整份装入以原策划为准，不能统一套用生产截断。未归营战利品不得提前计入公共资源。

## 5. 职责与系统边界

已确认的目标结构：

```text
KunWuAdmin 管理界面 → 管理配置 API → 草稿/审核 → 不可变配置版本
                                                       ↓
Godot 灵源院界面 → 玩家业务 API → 生产结算与统一资源事务 → 玩家状态/流水
```

- Godot：保留营地入口、375×817 页面规范；负责输入、显示、提示与可恢复的本地缓存。UI 不计算可入账收益。
- 玩家业务服务：验证身份、解锁和余额，以服务端时间结算，管理事务、状态版本和请求去重。不能信任客户端提交的时间、产出或任务完成声明。
- KunWuAdmin：复用现有配置集、实体 revision、审核、校验、发布体系，新增资源与生产管理能力；管理凭据不进入客户端。
- 部署形式为技术设计事项：可先在 KunWuAdmin 内设独立玩家业务模块与路由，逻辑上隔离管理/玩家权限，后续再拆部署，不要求第一期建立微服务。
- Godot 运行不得读取制作文档或相邻仓库。离线开发模式与在线玩家状态必须隔离；服务故障不能退回本地记账后自动合并。

## 6. 灵源院功能要求

### 6.1 冻结玩法基线

- 五种岗位；灵晶到达地图 2 解锁，庚精到达地图 3 解锁，按永久最高进度判断。
- 每名杂役每周期产量依次为 12、6、3、1、庚精每两周期 1；非灵粮每周期维护 2 灵粮。
- 初始 6 名，最多 12 名；第 7–12 名依次花费 300/450/650/900/1200/1600 灵粮。
- 五种储量初始 1 级、最高 5 级；完整容量与升级费用读取后勤分册 §3.3。
- 周期只从灵液等级派生为 30/25/20 秒；15/10 秒不在 1.0 开放。
- 在线/离线用同一结算规则，无独立离线时长上限、倍率或手动领取。

### 6.2 状态与结算

`V10-RES-010`：进入营地、打开灵源院、恢复连接、周期到期刷新及资源变更前均可触发结算；退出请求不是正确性前提，强退后仍可补算。

`V10-RES-011`：结算返回起止时间、有效时长、配置版本分段、各资源产出/维护/实际入库/溢出、缺粮暂停原因和未完成进度。净增量允许为负，库存不允许为负。

`V10-RES-012`：周期开始先检查容量，满仓或超容量的岗位停工、不扣维护、不推进生产进度；其他非粮岗位再按规定顺序支付完整维护，粮不足则本周期暂停。暂停不增加庚精成功周期。有空间且维护足够时自动恢复，不补发停工时段收益。周期开始尚有空间但本次产物超过空间时，按原完整周期维护收费，仅入库可容纳部分、报告溢出，之后满仓停工；不按入库比例退维护。灵粮岗位按同样容量规则停产，但本身无维护费。

`V10-RES-013`：长期离线计算必须与按事件逐周期结算的结果一致。可以按满仓、缺粮、配置生效等节点批量计算；不允许通过限制结算次数悄悄减少收益。

### 6.3 分配、招募、升级与灵液

`V10-RES-020`：调岗提交目标分配，先结算旧状态，再校验岗位解锁、非负整数人数与总人数限制；新分配和进度原子保存，按钮连点顺序处理。

`V10-RES-021`：招募弹窗显示当前人数、本次费用和结果人数。执行时重新计算费用；扣款、加人、锚点和流水同成同败。达到 12 名后显示上限。

`V10-RES-022`：储量升级显示当前/下级容量与灵木费用；先结算旧容量，历史溢出不补发，再原子扣款升级。缺少配置时禁用，不能使用无限容量默认值。

`V10-RES-023`：任务系统以唯一 `reward_claim_id` 提交灵液奖励；先结算旧周期，再验证合法任务节点、记领取记录与等级。重复请求只回显；失败回滚资源、等级和进度。加速保留个人未完成周期比例，例如旧 30 秒周期完成 15 秒，转为 25 秒后进度为 12.5 秒；不能立即重复兑换整周期收益。庚精成功周期余数保持不变。

### 6.4 客户端反馈

`V10-RES-030`：显示人数、库存/容量、岗位净产量、周期进度、灵液档位及最近结算。产量预测与已入库余额清晰区分。

`V10-RES-031`：覆盖加载、提交中、未解锁、无空闲杂役、余额不足、满仓、满级、数据缺失、连接中断、请求失败与状态冲突。失败不显示操作已经成功。

`V10-RES-032`：响应包含状态版本；旧响应不覆盖新状态。请求超时使用原请求 ID 查询/重试，不能生成新 ID 盲目再扣款；重连获取服务端快照。

## 7. KunWuAdmin 页面需求

| 页面/区域 | 必需内容与操作 | 验收要求 |
|---|---|---|
| 资源目录与详情 | code、分类、名称键、图标、容量策略、用途/来源引用、启停状态 | 可筛选与编辑；已引用资源不能硬删除；稳定 code 不随显示名修改 |
| 灵源院生产配置 | 五个岗位、产出周期数、维护、供给顺序、解锁条件、灵液档位 | 不把庚精每两周期产 1 存成整数每周期 0；区分 D0 停工字段与 1.0 供给语义 |
| 杂役与储量配置 | 初始/上限人数、逐人招募成本、五类五级容量与升级费用 | 表格完整、引用有效，费用在合法前置容量下可达到 |
| 生产模拟 | 输入库存、分配、进度、等级、时长；输出维护、入库、溢出与暂停 | 至少提供 10 分钟、1 小时、24 小时和自定义时长，不设置“离线上限”作为 1.0 规则 |
| 校验、差异与发布 | 字段差异、关联影响、错误位置、审核、发布版本和生效时间 | 复用已有门禁；草稿不影响玩家；修改后旧审核失效 |
| 玩家状态、余额调整与流水 | 查询余额、岗位、等级和流水；有权限者可增加、扣减或设置目标余额 | 调整前展示最新余额与变化，填写原因；统一事务记账；模拟不入真实账；管理员身份与玩家身份隔离 |

`V10-RES-040`：模拟与实际结算复用同一规则实现或同一套权威契约测试，不允许管理页维护另一个简化算法。

`V10-RES-041`：发布阻断至少包括资源混淆、引用缺失、等级表缺行、负值/非整数、非法人数、重复供给顺序、庚精周期缺失、灵液超出 1.0 档位及未解决迁移冲突。D0 与 v1_0 校验按配置集隔离。

`V10-RES-042`：发布版本不可变，记录明确生效时间并分段结算。回退创建新的生效记录，不撤销已发生的玩家流水。降容量不销毁已有库存，超容量按满仓停工且不耗粮，消耗至容量以下后恢复。

### 7.1 后台余额调整

`V10-RES-043`：首期支持本期五类生产资源的增加、扣减、设置目标余额。进入调整表单时先同步结算，展示玩家、环境、资源、最新余额、容量和状态版本；预览调整后余额，原因必填。提交使用管理员身份、独立资源调整权限、原请求 ID 和预期状态版本，不直接更新数据库余额列。

`V10-RES-044`：提交时先结算生产，再校验预期版本与当前余额。期间发生变化则返回最新状态，要求刷新后重新提交，不能盲目覆盖；目标值与扣减不能导致负数。普通增加/设置不得把余额提高到当前容量以上；降容量造成的已有超额库存允许保留或向下调整，不允许进一步增加。被拒绝的调整不写入调整流水，已合法完成的生产结算仍可返回最新快照。

`V10-RES-045`：调整余额、审计记录、资源流水及请求去重结果在同一事务内提交，记录操作人、时间、原因、目标玩家、环境、前后余额、差额和请求号；失败不得只改余额而漏流水。重试不重复生效，客户端按状态版本刷新。错误调整以新的反向调整修复，保留原记录，不删除历史。

`V10-RES-046`：满仓停工的资源被调低后，从调整生效时间恢复；被调至满仓后停工。调粮可影响后续岗位供给，不追溯改变已结算周期。玩家 API 无权调用管理调整能力。接口契约应覆盖无权限、并发冲突、负数、超容量、重复提交、事务失败和客户端刷新。

## 8. 业务接口与数据契约（能力级，路由待技术设计）

| 能力 | 客户端提交 | 服务返回 |
|---|---|---|
| 同步并结算灵源院 | 结算原因、请求 ID | 权威快照与结算报告 |
| 设置岗位分配 | 目标分配、预期状态版本、请求 ID | 更新后的快照、旧配置结算报告 |
| 招募一名杂役 | 预期状态版本、请求 ID | 实际扣款、新人数和快照 |
| 升级指定储量 | 资源 code、预期状态版本、请求 ID | 实际扣款、新等级和快照 |
| 查询请求结果 | 原请求 ID | 原结果或处理中/未找到状态 |
| 查询最近结算 | 查询条件 | 历史报告，不重复发放 |

会产生结算写入的同步操作采用显式命令接口，不放在可缓存/预取的只读 GET 上。客户端不得指定玩家身份覆盖认证主体、不得提交可信结算时间或最终库存。

最小持久化信息：

- 玩家身份、库存、杂役与分配、五类储量等级、最高地图进度、灵液等级及领取集合。
